## 1. 背景

客户未付款要扣货、付清要放货，现在多为一票一票操作，效率低。混装柜还需按原货物类型通知各部门。

扣货只表示**先不发货**；仓内提柜、拆柜、还空仍要做。货件管理以 Move Type 为准，扣货后票面须为「扣货」，列表才对齐。

---

## 2. 目标

1. 支持**整柜/批量**把 Move Type 改为扣货，以及放货恢复。
2. 扣货中的货**不能安排出库**；拆柜、还空不受阻。
3. 拆柜报告仍能按业务需要合板（含按 FBA Code 合并）；与「扣货后从合并组拎出」的现有逻辑兼容。
4. 整柜扣货/放货后，按**原渠道**通知对应仓库部门。

---

## 3. 场景及对应业务操作

只分两种场景，操作落点不同。

### 3.1 拆柜前扣货

| 步骤 | 做什么 |
|------|--------|
| 1 | 在**编辑计划**中支持**批量修改 Move Type** 为「扣货」（整柜勾选一次改完）；保留原 Move Type，放货时恢复。 |
| 2 | **建立拆柜报告**时：票面已是扣货，但仍按**原渠道 / 原 FBA Code** 参与合并（扣货票也要能按 FBA Code 合并），正常拆柜、打板。 |
| 3 | 各出库入口：Move Type 为扣货的货**不可安排出库**。 |
| 4 | 整柜批量改为扣货后：按各票**原 Move Type** 分组通知仓库领导及对应部门（FBA、私仓、自提、快递、留仓等）。 |

**与现有逻辑的关系（须兼容，不要拆两套）：**

- 今天：正常 FBA 货合并后，在报告里点「扣货」，会把该票从合并组**拎出来**单独成扣货。
- 拆柜前已是扣货、建立报告时：需要**按原 FBA Code 仍能合并**（与上一条方向相反，但是两个时机）。
- 实现时按时机区分即可：
  - **报告建立时**：已扣货票 → 仍按原渠道/FBA Code 合并；
  - **报告内再点扣货**：从当前合并组拎出（保持现逻辑）。

### 3.2 拆柜后扣货

| 步骤 | 做什么 |
|------|--------|
| 1 | 在**修改拆柜报告**里对该票扣货 / 取消扣货（沿用现能力：改 Move Type、保留原类型、从合并组拎出等）。 |
| 2 | 在**各自出库页面**也可扣货 / 放货，写入同一套 Move Type 状态，并拦住安排出库。 |

拆柜后不再走「编辑计划批量改类型」为主路径；以报告修改 + 出库页精细扣为主。

---

## 4. 几条硬规则（不分场景）

1. **Move Type = 扣货** 表示扣货中；货件管理、扣货 Tab 以此为准。
2. **放货** = 恢复为扣货前保存的原 Move Type。
3. **发货一律拦截**（安排出库 / 派送 / 装车）；提柜、拆柜、还空不拦截。
4. **查验扣货**（重点标记）与未付款扣货分开，不混用。

---

## 5. 主要改动点

| 位置 | 改动 |
|------|------|
| 编辑计划 | 新增：批量将 Move Type 改为扣货 / 批量放货恢复 |
| 建立拆柜报告 | 已扣货票按原渠道、原 FBA Code 仍可合并；可标明暂缓发货 |
| 修改拆柜报告 | 保持单票扣货/取消扣货（含从合并组拎出） |
| 各出库页 | 扣货真改 Move Type；安排出库前拦截扣货票 |
| 通知 | 批量扣货/放货后按原渠道通知各部门 |

---

## 6. 验收要点

1. 拆柜前：编辑计划批量改扣货后，货件管理显示扣货；能建拆柜报告且按原 FBA Code/原渠道合并；不能出库。
2. 报告内对已合并 FBA 再点扣货：该票从合并组拎出（现逻辑仍在）。
3. 拆柜后：改报告或出库页扣货后不能出库；放货后恢复原类型且可出库。
4. 批量扣货/放货有按原渠道的部门通知。
